# CC Collector — Requirements Specification

| | |
|---|---|
| **Document** | CC Collector requirements |
| **Version** | 0.1 — draft for review |
| **Status** | Open questions unresolved (§21). Not approved for implementation. |
| **Scope** | Continuous Collection only. Capture and land. |
| **Licence intent** | Apache 2.0, permissive dependencies only |
| **Out of scope by decision** | CDC connectors, outcome joins, reward computation, verifiers, CT/training export, UI |

---

## 1. Glossary

| Term | Meaning in this document |
|---|---|
| **Episode** | One complete agent trajectory: an ordered set of steps from task start to terminal state, including retries and abandoned branches. The unit of record. |
| **Step** | One action inside an episode — an LLM call, a tool call, a retrieval, or a human intervention. |
| **Producer** | Anything that emits telemetry to the collector: an instrumented app, a gateway, a file, the CLI importer. |
| **Source** | A configured ingest path inside the collector (one OTLP listener, one webhook endpoint, one file tail). |
| **Sink** | A configured output destination (object store, local filesystem, Kafka). |
| **Blob** | A payload stored outside the row, addressed by content hash. |
| **Entity key** | A business identifier extracted from a step (`ticket_id`, `order_id`) that will later allow joining to outcomes. Extracted in v1, joined in a later version. |
| **Trainable span** | A token range that was generated by the model, as opposed to tool output or injected context. |
| **Group** | N rollouts of the same task instance. Carried if a producer supplies it; the collector never creates groups. |
| **Quarantine** | A durable location for records the collector refuses to emit, retained for inspection rather than dropped. |

---

## 2. Problem statement

Teams running production agents already emit telemetry, but what they keep is shaped for humans reading a trace UI:

- prompts and tool results are truncated to fit a display
- retries and abandoned branches are flattened into a linear list
- fields needed to re-execute a step — seed, tool version, exact parameters — are dropped
- payloads live in a system with 7–30 day retention
- the identifiers that connect a trajectory to a business record are buried in tool arguments and never extracted

The result is telemetry that can explain an incident but cannot be scored by a verifier written three months later, and cannot be replayed.

**The collector's job:** capture everything an offline scorer or a future trainer would need, redact what must never leave the perimeter, and land it in cheap, durable, queryable storage — with no opinion about what reads it afterwards.

### 2.1 Goals

| ID | Goal |
|---|---|
| G-1 | Capture agent trajectories at a fidelity sufficient for offline replay and scoring |
| G-2 | Work with instrumentation teams already run — never require a rewrite |
| G-3 | Never let unredacted sensitive data reach storage or logs |
| G-4 | Survive sink outages and process restarts without losing acknowledged data |
| G-5 | Deploy like existing telemetry agents — a binary, a container, a Helm chart |
| G-6 | Be adoptable as an open-source component independent of any commercial product |

### 2.2 Non-goals

| ID | Non-goal | Rationale |
|---|---|---|
| N-1 | Change data capture from systems of record | Separate problem, separate release. An HTTP endpoint (§9.4) is the v1 substitute. |
| N-2 | Joining trajectories to outcomes | Requires watermarks and as-of semantics. Deferred. |
| N-3 | Computing rewards or running verifiers | The collector has no opinion about correctness. |
| N-4 | Training-set export | CT concern. Readers consume Parquet directly. |
| N-5 | A UI, search, or alerting | DuckDB, Trino and existing tools cover this. |
| N-6 | Being a general-purpose observability agent | It collects one shape of data well. |

### 2.3 Reserved surface

The schema **defines** `outcomes`, `labels` and `rewards`, and every episode carries `entity_keys[]`. The collector creates these tables empty and never writes to them in v1.

This is deliberate: it costs nothing now, and it means the join (N-1, N-2) and CT export (N-4) arrive as additive schema changes rather than a major version bump that breaks every reader.

## 3. Stakeholders

| Stakeholder | What they need | What makes them reject it |
|---|---|---|
| **Platform engineer** — deploys and operates | Helm chart, bounded memory, no new datastore, clear metrics | An OOM that takes down a production pod; an agent that needs its own database |
| **ML engineer** — consumes the data | Stable schema, verbatim payloads, files readable by DuckDB without a running service | Truncated prompts; a schema that changes under them |
| **Security reviewer** — approves it | Proof of what is redacted, an explicit data-flow diagram, SBOM, customer-managed keys | Payloads in debug logs; unexplained egress; a vendored dependency with an unclear licence |
| **Application developer** — instruments it | Zero code change where OpenInference already works; three lines where it doesn't | Being asked to adopt a new framework |
| **Verifier lab (internal consumer)** | Enough fidelity to replay an episode and score it with a verifier written later | Missing tool versions, missing parameters, flattened retries |
| **OSS contributor** | A spec, conformance tests, clean plugin boundaries | A monolith where adding a sink means understanding the whole pipeline |

## 4. Use cases

### UC-1 — Zero-code capture at the gateway
**Actor:** platform engineer.
**Precondition:** all LLM traffic routes through LiteLLM, Portkey or a similar gateway.
**Flow:** gateway posts a callback per completion → collector maps the payload via a declarative mapping file → groups calls into episodes by session id → emits on terminal marker or window expiry.
**Value:** organisation-wide coverage with no application change.
**Limitation:** no application context — tool calls made outside the gateway are invisible.

### UC-2 — Framework capture via OpenInference or OTel GenAI
**Actor:** application developer.
**Precondition:** app instrumented with OpenInference or OTel GenAI instrumentation.
**Flow:** app exports OTLP to the collector (in addition to whatever tracing backend it already uses) → collector normalises attributes → assembles episodes from the span tree.
**Value:** full trajectory including tool calls, retries, and framework structure.

### UC-3 — Explicit SDK emit
**Actor:** ML engineer with a custom agent loop.
**Flow:** code calls `episode.begin()`, `episode.step()`, `episode.end()` directly, supplying fields auto-instrumentation cannot see: tool versions, token spans, trainable masks, group ids.
**Value:** highest fidelity; the reference implementation of the format.

### UC-4 — Historical backfill
**Actor:** ML engineer evaluating the collector.
**Flow:** `cc import langfuse --from export.json` (or Phoenix, LangSmith, JSONL, Parquet) → records land in the same tables as live traffic, tagged with their source.
**Value:** a design partner can be evaluated before any deployment happens. This is the first thing a pilot uses.

### UC-5 — Local development
**Actor:** OSS contributor.
**Flow:** `docker run` with a local filesystem sink → generate traffic → inspect with DuckDB.
**Requirement:** no cloud account, no credentials, no Kubernetes needed to contribute.

### UC-6 — In-VPC with no egress
**Actor:** security reviewer at an enterprise.
**Flow:** collector deployed inside the customer's network, writing only to their bucket.
**Requirement:** the only outbound connection is to object storage. Every other destination is opt-in and visible in config.

### UC-7 — Sidecar with strict tenancy
**Actor:** platform engineer in a multi-team cluster.
**Flow:** one collector per pod, one bucket prefix per team, no shared process boundary.
**Requirement:** idle footprint small enough to run hundreds of copies.

## 5. System context

```
  producers                         collector                        storage
  ─────────                         ─────────                        ───────
  instrumented app  ──OTLP──┐
  gateway callback  ──HTTP──┤     ┌─────────────┐
  native SDK        ──HTTP──┼───▶ │  receive    │
  log file          ──tail──┤     │  normalise  │
  CLI import        ──file──┘     │  assemble   │
                                  │  redact     │
                                  │  extract    │  ──Parquet──▶  object store
                                  │  sample     │  ──blobs────▶  (S3/GCS/R2/MinIO)
                                  │  buffer     │
                                  └─────────────┘  ──DLQ──────▶  quarantine prefix
                                        │
                                        └──metrics/traces──▶ Prometheus / OTLP
```

**Trust boundary:** everything left of the sink runs inside the customer perimeter. Redaction happens before the buffer, so even the on-disk buffer contains no unredacted payloads.

## 6. Functional requirements

Priority: **MUST** — required for v1. **SHOULD** — required unless it threatens the milestone. **MAY** — accepted if contributed, not scheduled.

### F-1 Ingest

| ID | Requirement | Priority |
|---|---|---|
| F-1.1 | Accept OTLP traces over gRPC and HTTP/protobuf, recognising OTel GenAI and OpenInference attribute conventions | MUST |
| F-1.2 | Accept native episode events over HTTP as JSON and protobuf | MUST |
| F-1.3 | Accept gateway callbacks (LiteLLM, Portkey, Helicone shapes) through a declarative mapping file, not compiled-in parsers | SHOULD |
| F-1.4 | Tail JSONL files and container stdout | SHOULD |
| F-1.5 | Consume from a Kafka topic | MAY |
| F-1.6 | Every source is independently enabled, named, and attributed on the records it produces | MUST |
| F-1.7 | Reject oversized requests with a clear error and a metric rather than buffering them | MUST |

**Acceptance:** a single collector instance ingests from at least three source types concurrently, and every emitted episode names the source that produced it.

### F-2 Normalisation

| ID | Requirement | Priority |
|---|---|---|
| F-2.1 | Map every supported convention onto one canonical step record (§7) | MUST |
| F-2.2 | Preserve unrecognised attributes verbatim in a `raw` map — normalisation is never lossy | MUST |
| F-2.3 | Record source, instrumentation library and version on every episode, so fidelity gaps are attributable later | MUST |
| F-2.4 | Mapping tables are data files, versioned with the spec, not compiled logic | SHOULD |
| F-2.5 | Unknown span kinds are retained as `kind=other` rather than dropped | MUST |

### F-3 Episode assembly

| ID | Requirement | Priority |
|---|---|---|
| F-3.1 | Group spans into episodes by session id, falling back to trace id, then to a configured attribute | MUST |
| F-3.2 | Tolerate out-of-order arrival within a configurable window (default 5 minutes) | MUST |
| F-3.3 | Emit on explicit terminal event or window expiry, marking `complete` or `timed_out` | MUST |
| F-3.4 | Preserve parent/child links so retries and branches survive as a tree, alongside a canonical linear ordering | MUST |
| F-3.5 | Handle spans arriving after emit by writing an append-only patch record; emitted episodes are never mutated | SHOULD |
| F-3.6 | Carry `group_id` when a producer supplies one | SHOULD |
| F-3.7 | Bound the assembly buffer: when the configured maximum of in-flight episodes is reached, emit the oldest early marked `evicted` rather than growing memory | MUST |
| F-3.8 | Assembly state survives restart, or is documented as best-effort with a metric for episodes lost to restart | SHOULD |

**Acceptance:** given a recorded span stream replayed in shuffled order with a 10% duplicate rate, emitted episodes are byte-identical to those from the ordered stream.

### F-4 Replay fidelity

| ID | Requirement | Priority |
|---|---|---|
| F-4.1 | Capture prompts, completions, tool arguments and tool results verbatim and untruncated, subject only to F-5 and F-9.7 | MUST |
| F-4.2 | Capture model id, provider, temperature, top_p, max_tokens, seed, stop sequences, tool name and tool version | MUST |
| F-4.3 | Capture token counts, finish reason, latency and cost when the source provides them | SHOULD |
| F-4.4 | Capture token spans marking model-generated versus tool/context output; mark `unknown` when the source cannot say | SHOULD |
| F-4.5 | Capture logprobs when present | MAY |
| F-4.6 | Record a fidelity flag per episode summarising which of the above were unavailable | SHOULD |

**Rationale for F-4.6:** a consumer must be able to filter to "episodes good enough to train on" without re-deriving that per field.

### F-5 Privacy and redaction

| ID | Requirement | Priority |
|---|---|---|
| F-5.1 | Field-level policies: allow-list, deny-list, regex, path-based (JSONPath/CEL) | MUST |
| F-5.2 | Deterministic tokenization with a per-tenant HMAC key, so the same identifier matches across records without being readable | MUST |
| F-5.3 | Redaction runs before any write to disk buffer, sink, or log | MUST |
| F-5.4 | Emit a redaction manifest — rule id, field path, match count — containing no payload values | MUST |
| F-5.5 | Fail closed: a policy that cannot be evaluated quarantines the record. Configurable; closed is the default | MUST |
| F-5.6 | Metadata-only mode that discards payloads entirely | SHOULD |
| F-5.7 | Per-source policy override | SHOULD |
| F-5.8 | Optional entity detection (names, addresses, card numbers) via an external service, never a compiled-in dependency | SHOULD |
| F-5.9 | `cc redact --test` evaluates policies against a sample file and prints what would change | MUST |

**Acceptance:** a seeded corpus of synthetic PII passes through with zero leaks in output; manifest counts match the seed exactly.

### F-6 Entity extraction

| ID | Requirement | Priority |
|---|---|---|
| F-6.1 | Extract business keys from tool arguments and results using per-tool JSONPath or CEL expressions from config | MUST |
| F-6.2 | Store as `entity_keys[]` on the episode; do not resolve, validate or join | MUST |
| F-6.3 | Report extraction coverage as a metric — the share of episodes with zero keys is the leading indicator that a future join will fail | SHOULD |
| F-6.4 | Extraction runs after redaction, over tokenized values, so keys remain joinable without being readable | MUST |

### F-7 Sampling and volume control

| ID | Requirement | Priority |
|---|---|---|
| F-7.1 | Head sampling by rate, per source and per tenant | MUST |
| F-7.2 | Tail rules evaluated after assembly: always keep errors, human-edited episodes, and producer-flagged episodes | MUST |
| F-7.3 | Per-tenant quota and rate limit with an explicit shed policy and a metric for what was shed | SHOULD |
| F-7.4 | Sampling decisions are recorded on the episode (`sampled_by`), so a consumer can reason about bias | SHOULD |

**Note:** sampling must never split an episode — the unit of sampling is the assembled episode, never the span.

### F-8 Buffering and delivery

| ID | Requirement | Priority |
|---|---|---|
| F-8.1 | Buffer to disk; survive process restart without losing acknowledged data | MUST |
| F-8.2 | Apply backpressure to sources when the buffer crosses a configurable threshold | MUST |
| F-8.3 | Retry with exponential backoff and jitter; dead-letter after N attempts | MUST |
| F-8.4 | At-least-once delivery with a stable idempotency key per record | MUST |
| F-8.5 | Buffer is bounded by bytes and by age; the eviction policy is explicit and observable | MUST |
| F-8.6 | Buffer contents are encrypted at rest when a key is configured | SHOULD |

### F-9 Storage

| ID | Requirement | Priority |
|---|---|---|
| F-9.1 | Write Parquet to any S3-compatible store (AWS S3, GCS, Azure Blob, R2, MinIO) | MUST |
| F-9.2 | Partition by `dt / tenant / task_type`, configurable | MUST |
| F-9.3 | Store payloads above a threshold as content-addressed blobs keyed by sha256, deduplicated | MUST |
| F-9.4 | Make files visible atomically; a reader never sees a partially written batch | MUST |
| F-9.5 | Roll files by size and time toward a compaction-friendly target (default 128–512 MB) | MUST |
| F-9.6 | Write a manifest per batch listing files, row counts, byte counts, schema version, time range | MUST |
| F-9.7 | Truncate payloads above a hard maximum with an explicit marker rather than failing the record | SHOULD |
| F-9.8 | Register tables in an Iceberg catalog (Glue, REST, Nessie) | SHOULD |
| F-9.9 | Secondary sinks: local filesystem, Postgres, ClickHouse, Kafka | MAY |

### F-10 Schema and compatibility

| ID | Requirement | Priority |
|---|---|---|
| F-10.1 | Semver the schema; changes within a major version are additive only | MUST |
| F-10.2 | Stamp `schema_version` on every record and in file metadata | MUST |
| F-10.3 | Publish JSON Schema, protobuf definitions, and a conformance suite others can run against their own producer | MUST |
| F-10.4 | Readers written against version X.Y must read X.Z (Z > Y) without modification | MUST |
| F-10.5 | Publish a sample dataset with the spec | SHOULD |

### F-11 Configuration and operations

| ID | Requirement | Priority |
|---|---|---|
| F-11.1 | Declarative YAML with environment interpolation; secrets from env, file or secret manager, never inline | MUST |
| F-11.2 | Expose `/healthz`, `/readyz`, Prometheus metrics, and its own traces via OTLP | MUST |
| F-11.3 | Validate and dry-run modes that report what a config would do to a sample record | MUST |
| F-11.4 | Hot-reload configuration without dropping in-flight data | SHOULD |
| F-11.5 | Graceful shutdown: stop accepting, flush buffer, exit within a configurable deadline | MUST |
| F-11.6 | Refuse to start on invalid config with a message naming the file, key and reason | MUST |

### F-12 Security

| ID | Requirement | Priority |
|---|---|---|
| F-12.1 | TLS and optional mTLS on every ingest path; per-source API keys | MUST |
| F-12.2 | Never write payload content to its own logs at any level, including debug | MUST |
| F-12.3 | Support bucket-side encryption with customer-managed keys | MUST |
| F-12.4 | Publish an SBOM and signed release artifacts | SHOULD |
| F-12.5 | Run as non-root in a distroless container with a read-only root filesystem apart from the buffer volume | MUST |
| F-12.6 | No outbound network calls other than to configured sinks and telemetry destinations — no update checks, no analytics | MUST |

### F-13 Extensibility

| ID | Requirement | Priority |
|---|---|---|
| F-13.1 | Sources, processors and sinks are interfaces; adding one is a self-contained package | MUST |
| F-13.2 | A `Scorer` interface exists in the open project so external systems can attach rewards later — the collector ships no implementation | SHOULD |
| F-13.3 | Ship as OpenTelemetry Collector components as well as a standalone binary | SHOULD |

### F-14 CLI

| ID | Requirement | Priority |
|---|---|---|
| F-14.1 | `cc run` — run with a config file | MUST |
| F-14.2 | `cc validate` — check config, exit non-zero on error | MUST |
| F-14.3 | `cc import <source> --from <path>` — backfill from an export | MUST |
| F-14.4 | `cc inspect <file>` — summarise a Parquet file or blob without a query engine | SHOULD |
| F-14.5 | `cc redact --test <file>` — show the effect of policies | MUST |
| F-14.6 | `cc replay <episode_id>` — print a reconstructed episode as readable text | SHOULD |

## 9. Wire API

### 9.1 `POST /v1/episodes` — native emit
Body: one episode or an array, JSON or protobuf. Idempotent on `episode_id`.
`202 Accepted` with counts. `400` with a field path on schema error. `429` on quota. `503` when the buffer is full (retryable, `Retry-After`).

### 9.2 `POST /v1/spans` — partial emit
Spans that the collector assembles into episodes. Same status codes.

### 9.3 `POST /v1/hooks/<name>` — gateway callbacks
Mapped by the named mapping file. Unknown fields land in `raw`.

### 9.4 `POST /v1/outcomes` — reserved endpoint
Accepts outcome records and writes them to the `outcomes` table. **No connectors, no polling, no CDC** — a customer's own job posts to it. Present so a design partner can prove the join by hand without the collector growing a CDC subsystem. *Pending Q-6.*

### 9.5 OTLP
Standard OTLP/gRPC (4317) and OTLP/HTTP (4318) receivers.

### 9.6 Operational
`GET /healthz`, `GET /readyz`, `GET /metrics`.

## 10. Configuration

```yaml
schema_version: "0.1.0"
tenant: acme

sources:
  - name: otlp
    type: otlp
    grpc: {listen: "0.0.0.0:4317", tls: {cert_file: /certs/tls.crt, key_file: /certs/tls.key}}
    http: {listen: "0.0.0.0:4318"}
  - name: litellm
    type: webhook
    path: /v1/hooks/litellm
    mapping: mappings/litellm.yaml
    auth: {type: bearer, token_env: CC_LITELLM_TOKEN}
  - name: agent-logs
    type: file
    include: ["/var/log/agents/*.jsonl"]

assembly:
  session_key: ["session.id", "gen_ai.conversation.id", "trace_id"]
  window: 5m
  max_in_flight: 50000
  emit_on: ["episode.end", "window_expiry"]

redaction:
  default: deny            # deny-by-default: only allow-listed paths survive
  on_error: quarantine     # F-5.5 fail closed
  allow:
    - "steps[*].content_inline"
    - "steps[*].tool_name"
  rules:
    - id: email
      match: {regex: "[\\w.+-]+@[\\w-]+\\.[\\w.]+"}
      action: tokenize
    - id: card
      match: {regex: "\\b(?:\\d[ -]*?){13,16}\\b"}
      action: drop
  tokenization:
    key_env: CC_HMAC_KEY

entities:
  - tool: zendesk.update_ticket
    keys:
      ticket_id: "$.args.id"
  - tool: stripe.create_refund
    keys:
      order_id: "$.result.metadata.order_id"

sampling:
  head: {rate: 1.0}
  tail:
    keep_if:
      - "episode.status != 'complete'"
      - "episode.error != null"
      - "episode.raw['human_edited'] == 'true'"
    otherwise_rate: 0.25

buffer:
  dir: /var/lib/cc/buffer
  max_bytes: 8Gi
  max_age: 24h
  backpressure_at: 0.8

sinks:
  - name: lake
    type: s3
    bucket: acme-agent-lake
    prefix: cc/
    region: us-east-1
    partition_by: ["dt", "tenant", "task_type"]
    target_file_bytes: 268435456
    roll_interval: 15m
    blob_threshold_bytes: 8192
    compression: zstd
    sse: {type: aws:kms, key_id: arn:aws:kms:...}

telemetry:
  metrics: {listen: "0.0.0.0:9464"}
  traces: {endpoint: "http://otel-collector:4317"}
  log_level: info
```

Every key is validated by `cc validate`; unknown keys are an error, not a warning.

## 11. Observability of the collector itself

## 12. Failure modes

| Condition | Behaviour | Signal |
|---|---|---|
| Sink unreachable | Buffer → backpressure at threshold → shed per sampling policy → dead-letter | `cc_buffer_bytes`, `cc_sink_errors_total` |
| Malformed record | Quarantine with reason; never silent drop | `cc_quarantined_total{reason}` |
| Episode never terminates | Emit at window expiry as `timed_out` | `cc_episodes_emitted_total{status}` |
| Assembly buffer at capacity | Emit oldest early as `evicted` | `cc_assembly_window_evictions_total` |
| Span arrives after emit | Append patch record; original immutable | `cc_episodes_emitted_total{status="patched"}` |
| Duplicate delivery | Stable idempotency key; reader deduplicates | — |
| Clock skew | Record producer and collector times both | `cc_clock_skew_seconds` |
| Oversized payload | Truncate with marker, keep the record | `truncated` field, counter |
| Redaction policy error | Fail closed — quarantine | `cc_redaction_errors_total` |
| Disk full | Refuse ingest with retryable 503; never corrupt the buffer | `cc_buffer_bytes` at max |
| Config invalid at reload | Keep running the previous config; log and increment | `cc_config_reload_errors_total` |
| Partial batch write | Manifest written last; readers ignore unmanifested files | — |

## 14. Security and privacy

**Data flow:** producers → collector (in perimeter) → object store (customer-owned). No other destination exists unless configured.

**Threats considered:**

| Threat | Mitigation |
|---|---|
| Sensitive payload reaching storage | Redaction before buffer (F-5.3), deny-by-default policy, fail closed (F-5.5) |
| Sensitive payload in collector logs | F-12.2, enforced by a lint rule in CI on log call sites |
| Sensitive payload in metric labels | §11 rule, enforced by review |
| Compromised collector exfiltrating data | F-12.6 no outbound except configured sinks; network policy documented in the Helm chart |
| Buffer disk seized or snapshotted | Redaction already applied; optional buffer encryption (F-8.6) |
| Tampered release binary | Signed artifacts, SBOM (F-12.4) |
| Tenant A reading tenant B | Single-tenant deployment (Q-5); bucket prefix + IAM boundary |
| Replay of ingest requests | Idempotency key, optional mTLS, per-source tokens |

**Key management:** the HMAC tokenization key never leaves the deployment and is supplied by env or secret manager. Rotating it breaks joinability of new records against old ones — this must be documented prominently, with a `key_id` recorded on each record so a rotation is detectable rather than silent.

## 18. Governance

- **Licence:** Apache 2.0 across spec, SDKs, collector and importers.
- **Contributions:** DCO sign-off, not a CLA.
- **Spec versioning:** semver; additive-only within a major; a documented deprecation window before any removal.
- **Naming:** neutral project name, distinct from any commercial product built on it (see Q-7).
- **Conformance:** the suite is the definition of compliance; anyone may claim it.

## 19. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Fidelity fields are unavailable from most instrumentation | Data is collected but not replayable | F-4.6 fidelity flags; SDK path (UC-3) for partners who need full fidelity |
| Entity extraction misconfigured | Episodes collected but unjoinable — discovered months later | F-6.3 coverage metric surfaced in docs and dashboards from day one |
| Convention churn in OTel GenAI / OpenInference | Mapping breaks on upgrade | F-2.4 mappings as versioned data; conformance tests pinned per convention version |
| Scope creep back into CDC/CT | v1 never ships | §2.2 non-goals are contractual; §9.4 is the pressure valve |
| Nobody adopts the format | Effort wasted on a spec | M1 proves value with zero deployment; adoption measured before M3 |
| Payload volume cost | Customers disable collection | Blob dedup, zstd, sampling, metadata-only mode |

## 20. Assumptions

- Producers can supply, or be configured to supply, a stable session identifier.
- Customers have or can create an object store bucket in their own account.
- Kubernetes is the primary deployment target; bare processes and Docker are supported but not optimised.
- v1 is single-tenant per deployment (pending Q-5).
- Clocks are roughly synchronised (NTP); skew is recorded, not corrected.
